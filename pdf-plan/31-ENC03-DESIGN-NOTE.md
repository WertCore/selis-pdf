## 2. The algorithm as implemented (Algorithm 1, ISO 32000-2 §7.6.6.4)

1. **Parse** the selected `/Recipients` blob as CMS `ContentInfo { id-envelopedData,
   EnvelopedData }` (RFC 5652 §6).
2. **Match + unwrap**: try each `RecipientInfo` under the supplied credential —
   `KeyTransRecipientInfo` (RSAES-PKCS1-v1_5, or RSAES-OAEP since ENC.08) or
   `KeyAgreeRecipientInfo` (ECDH static-stdDH + SHA-256 X9.63 KDF + AES-KW, RFC 5753 §2.1.1)
   — to recover the CEK.
3. **Decrypt** the `EncryptedContentInfo`'s content with the CEK. AES-128/192/256-CBC is
   the modern set (IV from the algorithm parameters, strict PKCS#7 validation, 8-byte-block
   TDEA-CBC and RC2-CBC and the RC4 stream of the `s3` era are the ENC.08 *reads* — §5). The
   payload is exactly **24 bytes: a 20-byte seed + the recipient's 4 permission bytes**, and
   that rule is enforced for every cipher: the CBC families after PKCS#7 stripping, RC4 (no
   padding) as the length the transport's unwrap produced.
4. **Derive** the file encryption key: `HASH(seed ‖ every recipient blob [‖ FFFFFFFF])`
   truncated to `/Length`/8 — SHA-256 for `/V 5` (AESV3), SHA-1 for `/V ≤ 4` (s3-era RC4 and
   AESV2). The hash spans all recipients (so no recipient can shorten another's key);
   `/EncryptMetadata false` appends the 4×`0xFF` marker.
5. Per-object stream/string decryption then follows the standard handler's algorithms
   with `/V` as the revision: V1–V3 → salted RC4 (Algorithm 1), V4 → salted AES-128
   (Algorithm 1), V5 → direct-key AES-256 (Algorithm 1a) — reusing
   `selis_crypto::decrypt_data` unchanged.

**A note on the task wording:** the task brief said "decrypt `/O` with the recipient key per
the spec's algorithm 1 §7.6.1". Public-key `/Encrypt` dictionaries have no `/O`/`/U`; the
recipient key unwraps the CEK, which decrypts the **seed** payload, and the file key is the
seed hash of step 4 (the PDFBox reference implementation matches this construction exactly).
The correct spec citations are ISO 32000-1:2008 §7.6.6 / ISO 32000-2:2020 §7.6.6.4 and
§7.6.3.3 Algorithm 1 for per-object keys.

## 3. Dependency decision: hand-rolled DER reader, `rsa` + `p256` for the crypto

The workspace had no DER parser. Both options allowed by the task were evaluated:

| | `der` crate 0.7 (RustCrypto/formats) | hand-rolled minimal reader (chosen) |
|---|---|---|
| Licence | MIT OR Apache-2.0 ✓ | n/a |
| Maintenance | Actively maintained (the substrate of `pkcs8`/`spki`/`x509-cert`) ✓ | ours, one file |
| no_std / wasm | ✓ | ✓ |
| Supply-chain cost | **Zero marginal** — `rsa` and `p256` already pull `der` transitively for PKCS#8 decoding | zero |
| Ergonomics for CMS | `RecipientIdentifier`/`originator` CHOICEs with untagged SEQUENCE variants and EXPLICIT wrappers need manual `Decode` impls anyway; the derive machinery does not buy much for ~10 constructs | full control over exactly the subset |
| Fuzz assurance | upstream-hardened | ours — but iterative (no recursion), `checked_*` lengths, `get()`-only access, dedicated `pkcs7_cms` target |

**Decision:** hand-roll the reader (`selis-crypto/src/der.rs`, ~200 lines, iterative — no
stack risk) and record it here. The CMS subset accepts exactly what §7.6.6 needs (SEQUENCE/
SET/OID/INTEGER/OCTET STRING/BIT STRING/NULL + context tags 0–1) and rejects everything
else — indefinite lengths, the high-tag-number form, non-minimal long lengths, trailing
bytes — as typed `ENCRYPT_MALFORMED`. RSA/EC **private-key** decoding stays inside
`rsa`/`p256` (their own hardened PKCS#8 decoders); hand-rolling RSA was never on the table.

New dependencies (all RustCrypto, MIT OR Apache-2.0, no_std+alloc, MSRV ≤ 1.82, actively
maintained, wasm32-clean — ADR-P0021 compliant):

| Crate | Version | Why |
|---|---|---|
| `rsa` | 0.9 | The only credible pure-Rust RSA implementation (RFC 8017 PKCS#1 v1.5 CEK transport). |
| `p256` | 0.13 | EC P-256 ECDH key agreement (`ecdh`, `pkcs8` features) for the CMS key-agreement path. |
| `sha1` | 0.10 | Algorithm 1's V4 hash is SHA-1 — format-defined, decrypt-only use. |

## 4. Certificate-selection policy: v1 first-match → §4.1 X.509 identity match (ENC.07)

> **§4.1 (below, shipped via SL-1.ENC.07 on 2026-09-14, pending human review) supersedes this
> section's original "no X.509" stance.** The sign-off decision in §8 anticipated it; what
> landed is an identity match, not a trust decision.

**Policy (v1, read-only — pre-ENC.07 text, kept for the record):** recipients are tried in
`/Recipients` array order; the first blob whose transport unwraps under the supplied
credential **and** whose content decrypts to a structurally valid 24-byte payload wins.
The credential is the private key alone (`PKCS#8 DER`).

**Policy (v2, §4.1):** `PubKeyCredential` carries key material *plus* an optional X.509
certificate chain (DER blobs, leaf first) and an explicit `match_by` knob —
`auto | first_valid | certificate` (default `auto`), which is the selectable behavior
every mainstream viewer has (Acrobat/Foxit/PDFium/qpdf/PDFBox all resolve the CMS
`RecipientIdentifier` against the supplied certificate when both are present).

- **Matching is done on the recipient-identifier bytes, before any unwrap** (RFC 5652
  §6): `issuerAndSerialNumber` — DER equality of the issuer `Name` plus *value*
  equality of the serial INTEGER ([`pkcs7::identifier_matches`, minimality-normalized]);
  `subjectKeyIdentifier` (`[0]`) — equality against the certificate's
  `subjectKeyIdentifier` extension or, absent one, the RFC 5280 method-1 SHA-1 over the
  subject public-key BIT STRING content (PDFBox's and .NET's `GetCertHash` fallback).
  The CMS blobs' original identifiers are now parsed into `KeyTransport::identifier`
  (`CmsRecipient` flattened into per-transport entries; a `KeyAgreeRecipientInfo` with
  several `RecipientEncryptedKey`s fans out to one transport per addressed key).
- **Modes:** `auto` = identity pass first; zero identity matches (identifier absent,
  wrong serial, or a bare key) falls through to the §4-v1 structural scan, an existing
  match that fails to unwrap also falls through. `first_valid` = v1-only draft
  behavior; the chain is ignored. `certificate` = identity match required: no
  chain, no match, or a matched-but-non-opening transport all yield typed
  `RECIPIENT_NO_MATCH` — **never** a silently-different addressed recipient.
- **`x509` is intentionally minimal** (`selis-crypto/src/x509.rs`): it reads exactly
  issuer/serial/SKI from `Certificate` and skips — structurally, never trusted —
  signature algorithm, validity and subject. **Certificate signatures are NOT
  verified** (same posture as PDFBox `CertId`/qpdf recipient matching: which key the
  credential holds is proven by the unwrap; a certificate is addressed with an
  identifier, opened with a key — never a trust decision, and the fixture certs
  deliberately carry placeholder signatures). New public parse entry points:
  `x509::parse_identity` and `pkcs7::decode_permission_block`/`payload_seed` —
  both budget-charged DER walks with `# Budget` / `# Malformed Input` rustdocs and
  their own fuzz targets (`x509_identity`, `pkcs7_perms`).
- **Selection is observable:** `PubKeyAuth` gained `matched_by` (`ByIssuerAndSerialNumber |
  BySubjectKeyIdentifier | Structurally`) and `recipient_index`, surfaced verbatim on the
  engine's `PublicKeyReceipt` — tests and shells can prove *which* recipient opened.
- **No write-path change** (ADR-P0019): identity selection is decrypt-side only;
  the fixture blobs/PDFs regenerated (new identifiers embedded, `/Recipients` blobs for
  the same fixtures) — `xtask pubkey-fixtures` + committed outputs.

**Why the v1 rationale still holds for a bare key:** wrong-key decryption is already
detected structurally — RSA PKCS#1 v1.5 padding check (fails with p ≈ 1−2⁻¹⁶), then
AES-CBC strict padding plus the exact 24-byte length (combined false-accept < 2⁻⁶⁰),
and AES-KW's integrity register (2⁻⁶⁴) on the ECDH path. What v1 lacked was (a) the
interop behavior (readers *do* address by identifier) and (b) the permission-block
binding (§6.2). It remains the honest fallback so a key-file-only user is never
blocked by a certificate they no longer have.

## 5. Refused (typed `ENCRYPT_UNSUPPORTED`, never silent) — ENC.08-shrunk

**ENC.03's original refusal list was `s3`/RC4/3DES/RC2/RSA-OAEP.** The HUMAN sign-off
(2026-09-12) superseded it — "support s3/3DES legacy files for decryption", competitor parity
with Acrobat/PDFium/PDFBox/qpdf/MuPDF — and **SL-1.ENC.08** implements it: the four legacy
content algorithms and the RSAES-OAEP transport decrypt on the **read path only** (no write
path exists at all, ADR-P0019 unchanged). What the refusal list claimed to protect — no
*silent* wrong-key decrypt — is provided differently, honestly:

| Was refused | Now |
|---|---|
| `adbe.pkcs7.s3` (`/V ≤ 3`, RC4-era) | **accepted (read-only)**: the *file* key comes from the Algorithm-1 seed hash and per-object crypto goes through the existing RC4 path in `decrypt_data`; the *envelope* cipher is the legacy set below. The original "RC4 has no padding, wrong key would be silent" concern is neutralised by ordering: the RSAES-PKCS1-v1_5 / RSAES-OAEP **unwrap** (a padding/hash integrity check on the CEK itself, `p ≈ 1−2⁻¹⁶` / better) runs *before* any content key exists; the RC4 arm additionally refuses any content that is not exactly the 24-byte payload. A wrong key therefore ends `RECIPIENT_NO_MATCH` exactly as on the AES path — never a *silently* wrong file key from an un-rejected transport. |
| RC4 / 3DES-CBC / RC2-CBC content | **accepted (read-only)** as above. Vendored FIPS 46-3 / RFC 2268 tables in `selis-crypto/src/legacy.rs` (§3 posture restated: `des` 0.5 / `rc2` 0.9 are licence-clean but *trait-incompatible* with this tree's `cipher` 0.4, and each would add `cargo vet` surface for museum-format-only code — see R20's sibling note); KAT-pinned to `openssl 1.1.1q` output. |
| RSA-OAEP key transport | **accepted (read-only)** since ENC.08 (id-RSAES-OAEP `1.2.840.113549.1.1.7` with `RSAES-OAEP-params` SHA-1/SHA-256, MGF1; SHA-384/512 too where `rsa` can build them); an `id-PSpecified` *non-empty* label is **refused typed** (the unwrap would silently differ on the label, and *no writer* emits one for PDF). |

**The refuse list after ENC.08** is just the genuinely-broken/unsupported:

| Refused | Why |
|---|---|
| `aes192`-wrap on ECDH (24-byte KEK) | RFC 5753 permits it, nothing in the corpus uses it, and the *wrapped length* filter skips it structurally (§6.5). Encounter-driven. |
| RSAES-OAEP digests outside SHA-1/224/256/384/512, non-MGF1 mask generators, non-empty `id-PSpecified` labels | Not OAEP PDFs-in-the-wild emit; refusing typed is the §5 never-silent rule for a *variant we cannot verify we got right*. |
| PasswordBasedRecipientInfo / OtherRecipientInfo | PBES2 is a different handler project (owner-password semantics, not a key-transport arm). |
| Detached CMS content (`encryptedContent` absent) | PDFs never detach; parsing a detached envelope would silently open with no payload rather than fail typed. |
| AES-*128*-key-wrap-of-a-*24*-byte CEK and other content/KEK length mismatches | `unwrap_cek`'s transport check (or the CBC padding + 24-byte length) reject them as a wrong-key try, typed. |
| PKCS#12 (.pfx) keystore parsing | Its own ASN.1+PBES2 project; the credential API takes PKCS#8 DER, which every keystore can export. |
| `unprotectedAttrs` | Tolerated and ignored (rarely present). |
| ECDH `ukm` | Tolerated and ignored (unused by static-stdDH schemes). |

## 6. Known limitations & accepted risks (for the human to weigh)

1. **RUSTSEC-2023-0071 (Marvin-style timing side channel in `rsa` decryption)** —
   unfixed upstream. Accepted here because the operation is a *local* decryption of the
   user's own document with the user's own key (no remote oracle surface); this is the same
   posture as every local PDF tool. A server-batch surface (`Surface::Server`) should
   revisit before shipping public-key decryption in a multi-tenant service. **ENC.08 is a
   partial mitigation:** the RSAES-OAEP arm is constant-time inside `rsa`, so a *new*
   envelope can be written by anyone who cares about this; the v1.5 arm stays accepted
   because every legacy document in the wild uses it (R18).
2. **Permission bits enforcement — shipped as SL-1.ENC.09 (read side).** The
   per-recipient 4-byte permission block (stronger than `/P`) is now consumed by the
   policy layer and gates Selis's own content operations (design note §6.2). This was the
   sign-off's *only* hard requirement ("what they don't: enforce the CMS recipient's
   permission bits, not just surface them"); the owner-password/standard-handler path
   keeps the SL-1.ENC.04 `/P`-only, logged-override posture (the recipient block binds
   *recipients*, never an owner who holds the whole document's key).
3. **Unknown security handlers still open tolerantly** (pre-existing behaviour, unchanged
   here): content stays garbage rather than the document being refused. If sign-off wants
   `ENCRYPT_UNSUPPORTED` for unknown `/Filter` names, that is a one-line follow-up.
4. **Committed test key material.** Two throwaway RSA-2048 private keys (PKCS#8 DER) live
   under `crates/selis-pdf-engine/tests/fixtures/` purely to build deterministic fixtures;
   they protect nothing and are flagged here per the "never commit secrets" rule (test
   fixtures are the accepted exception, but the human should see them in the diff).
5. **`aes192`-wrap ECDH KEKs** (24-byte KEK) are skipped structurally (wrapped length
   filter); only 128/256-bit KEKs unwrap. Encounter-driven addition if ever seen.
6. **The seed hash depends on the whole `/Recipients` array** (per spec). Re-saving a
   public-key document with a *different* recipient set therefore changes every existing
   recipient's file key — inherent to the format, noted so future write-path work
   (out of scope per ADR-P0019) does not rediscover it the hard way.
7. **The legacy fixtures are synthetic, not recovered wild files (ENC.08 honesty clause).**
   The task asked for three RC4-CMS-era documents *from the corpus* "if licensed"; a sweep of
   the local corpus for `adbe.pkcs7` found **zero** public-key documents (RC4-era or not), and
   public-key PDFs are the one encryption class the fetched wild corpora do not carry (the
   recipient key must exist for the file to be readable at all). What ENC.08 shipped instead is
   deterministic in-repo material from `xtask pubkey-fixtures` — same DER shapes and cipher
   suite (RC4-40/128, TDEA, RC2) as Acrobat-era envelopes — whose cipher constants were
   verified against `openssl enc`. **A genuine 2003–2009 public-key PDF opening here is still
   evidence we do not have**; the corpus is fetch-only, so this is the human/CI step that
   stays outstanding for a conformance claim (no §8.10 "we support the format" claim is made).
8. **`decrypt_payload`'s RC4 arm has *no* padding check (by cipher construction).** Its gate is
   the transport unwrap + the exactly-24-byte content rule; those are checked on every read and
   the fuzz target asserts both (§7). This is documented because it is *not* the same
   strength of accidental-accept defence as the AES path (2⁻¹⁶ vs. p ≈ 2⁻¹⁶ padding + 24-byte
   length) and a reviewer should see that difference stated, not buried.

### §6.2 note — `/P` versus the CMS recipient block (SL-1.ENC.09, 2026-09-14)

They are *different kinds of statements*, and now behave differently:

| | PDF `/P` (standard handler) | CMS recipient block (public-key handler) |
|---|---|---|
| Who wrote it | the *encryptor* (document-level) | the encryptor **per recipient**, inside that recipient's wrapped payload |
| How it binds | plaintext metadata — anyone with the file key can read it, anyone with a PDF editor can rewrite it | cryptographically attested to whom it applies: it is only *visible* after that recipient's key unwrapped the CEK (or ECDH-agreed the KEK) and the AES-CBC payload decrypted — possessing the block **is** being the recipient |
| Selis posture (ENC.04 vs ENC.09) | surfaced honestly; owner-password path keeps `/P`-only semantics with the explicit logged override | **enforced through the policy layer as the *API*:** every content-touching `ContentOp` (print/render, text copy/extract, annotate, redact/edit, form-fill) is checked against the intersection |
| Combination | — | `effective = /P ∧ CMS` (`Permissions::restrict`): the weaker CMS grant never raises the PDF-level grant, and `/P -4` in the fixtures demonstrates denials coming *only* from the CMS block |
| Absent / damaged | `/P` default `0xFFFF_FFFF` when the public-key dict omits it (then the recipient block binds alone) | a payload that is not exactly 24 bytes decodes `None` — the selection loop keeps scanning or fails `RECIPIENT_NO_MATCH`; `decode_permission_block` never yields a silent zero/default grant (fuzz: `pkcs7_perms`) |

Wiring: `selis-policy::ContentOp` + `check_permissions` (new typed code **1808
`PERMISSION_DENIED_BY_CMS`**, Policy/Unchanged, in the enc/perms range); the engine's
public-key open stores a `PublicKeyReceipt { cms_permissions, pdf_permissions,
matched_by, recipient_index }` on the session (`Session::open_as_recipient`,
`Session::recipient_receipt`, `Session::check_permissions`), and every wired content
egress consults it (`embedded_file_data` → `CopyText` gate; the redact/annotate/edit
ops landing with the write paths must call the same function — Phase 5). The viewer UI
greying is Phase 4 (SL-5); here the *API* is the gate. `Session::open` (no credential)
and the standard handler are unchanged — no receipt, no CMS binding.

## 9. Risk register (new)

**R18 — Marvin / RSA private-op timing side channel in PKCS#1 v1.5 CEK unwrap** (local read-only
accept).

- **Severity:** medium → high if `Surface::Server` is enabled → existential for multi-tenant cloud
  PDF decrypt *for other people's files*
- **Trigger:** Selis exposing any public-key CMS decrypt to a *server-side*, *multi-user*, or
  *unauthenticated* endpoint (i.e. Selis's own keys are not the only thing in the session).
- **Status:** accepted in local mode only (the user's key, the user's file; Acrobat/PDFium/PDFBox
  have the same class of issue and Adobe/PDFium still ship it for the local case).
- **Mitigation:** any batch/server mode *must* use constant-time or hardware-accelerated RSA, or
  must reject `pkcs1` v1.5 transport and require OAEP. This is a `check-permissions` gate on the
  server, not on the SDK.
- **Kill criterion:** a server-side product is announced with this code unmodified → block feature.

**Note:** `adbe.pkcs7.s3` (RC4) also has a *different* attack surface (a known plaintext on 40-bit
versions, trivially, and 128-bit RC4 has known keystream attacks). This is *not* why we do *not*
enforce RC4 in read mode for the "encrypted-legacy" corpus. We *do* enforce the permission bits as
policy (read-only, no silent decrypts). A read-only decrypt is not the same as "an unauthenticated
endpoint decrypting a random attacker's file with our server's keys" (there is no such thing in
local mode; ENC.07/08 are read-only, so the SDK never touches a wrong key).

**R19 — deprecated `generic-array` surface redens the nightly `fuzz-soak` job** (fixed by
SL-1.ENC.08 as delivered; the regression risk stays, hence this entry).

- **Trigger:** `generic-array` 0.14.8+ carries a crate-level `#[deprecated]` ("upgrade to
  generic-array 1.x"), so under `cargo +nightly` with `RUSTFLAGS=-D warnings` (what CI's
  `fuzz-soak` uses) **every** inherent generic-array call in a fuzz-built crate was a hard
  compile error (`aes::cipher::Block::clone_from_slice`, `digest::Output::as_slice`, …) — not a
  warning. The fuzz job went red on every target from nightly ≥ 2026-09-11 and stayed red
  until ENC.08's branch (the SL-1.ROB.06 note records the diagnosis; the fix landed here).
- **Why it is *not* behaviour:** no cipher, key schedule, DER path or selection logic changed;
  the AES/KW/CBC code now builds its blocks with `[u8; N]: Into<Block>`, reads them through the
  `Deref`/slice coercions, and the digest output through `AsRef`/`hash.finalize()`-as-buffer.
- **Regression guard:** `selis-crypto/src/lib.rs` carries `#![deny(deprecated)]` (verified against
  `generic-array` 0.14.9 in the workspace `Cargo.lock`) so a new deprecated intrinsic call fails
  the crate build immediately instead of waiting for the nightly fuzz job. Verify locally with
  `cd fuzz && CARGO_TARGET_DIR=<shared> RUSTFLAGS='-D warnings' cargo +nightly check`.
- **Severity:** CI availability, not security. **Status:** fixed (2026-09-16).
