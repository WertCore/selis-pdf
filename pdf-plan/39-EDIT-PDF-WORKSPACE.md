# 39 — The `/edit-pdf/` workspace: a document editor, not a form

**Status:** Slice 1 shipped. **Owner:** AI+ · **Depends on:** `34-TOOLS-SITE-ROADMAP.md`,
`23-EDIT-MODEL-SPEC.md`, `36-TOOLS-PAGE-NAV-AND-ROUTES.md`, SL-4.WEB.01/03, SL-5.TEXTEDIT.01/02.
**Rule inherited from 35:** a box is ticked only when the slice ships through the owned engine, has
unit/browser evidence, and is documented. No box is ticked for a mock or a local-only run.

## Why this file exists

The tools site is a catalogue of **one-shot operations**: drop a file, set a few options, press Run,
download the result. Every one of the 47 cards is that shape, and the card is the unit of the
registry, the sitemap, the service-worker precache and the browser harness.

That shape cannot express "a PDF editor". A reader who opens the site and asks *what can I do to
this document?* gets 47 forms, none of which is a document. The one editing primitive that does
exist — `edit_text`, one find/replace over one page — is buried behind a card that looks like every
other card.

`23-EDIT-MODEL-SPEC.md` defines the long-term edit model (a mutation journal, undo groups, a
materialised document). None of it is built: every `SL-5.EDIT.*` and `SL-5.TEXTEDIT.*` box in
`15-PHASE-5-edit.md` is unticked, and `selis-pdf-wasm-editor` is a 4 988-byte stub that no page
fetches. Building the whole journal is a multi-month project and it is not what a reader is missing
today.

What a reader is missing today is a **surface**: a document on screen, with the tools to change it,
and a way to take the result away. That is a shell problem before it is an engine problem, and this
slice is the shell.

## What this slice is

A new top-level route, `/edit-pdf/`, that is a **document workspace**:

- The document is rendered on screen, continuously, as pages — the same rendering path the viewer
  uses, with the same text layer over it.
- **Click any text line and type over it.** The edit is the engine's own `edit_text`, applied to the
  line the user actually clicked (the line's own text is the search key, and the engine replaces the
  *first* show-text operand that carries it — the same primitive the viewer's edit mode already uses,
  now driven by a click rather than a form).
- **Undo and redo**, over the edit history, with the document's bytes preserved per step so an undo
  is an exact restore rather than a re-derivation.
- **Page operations** on the open document: rotate, delete, reorder, duplicate, insert blank — the
  engine's existing tools-chunk operations, applied to the *current* state of the document.
- **Download** the edited document, as a Blob in this tab, never uploaded.

The editor is honest about what it cannot do, in the copy rather than in a promise: editing a line
replaces the text in place and does **not** re-flow the paragraph, a line drawn as several separate
runs can only have one of them replaced, and the text must be one the engine can address. Those
limits are `SL-5.TEXTEDIT.02` and `SL-5.TEXTEDIT.04`, and they are stated on the page.

## Decisions

- **D1 — A top-level route, not a card.** The registry is a catalogue of one-shot operations and
  every card in it is one. A workspace is a different shape: it holds a document open across many
  operations, and the standard workspace shell (dropzone → options → Run → result card) has no
  place to put an undo stack or a page rail. So `/edit-pdf/` is its own page, like `/viewer.html`
  is its own page — and unlike the 47 cards it is not in the tool registry, because the registry's
  `ToolDef` cannot describe it (a card has one verb, one input set and one output).
  *Consequence:* the card count stays 47, the harness's `TOOLS_PAGE_CARDS` is untouched, and the
  editor is a by-URL surface like the three the harness already drives (`TOOLS_PAGE_BY_URL`).
  The page is **hand-authored** (`public/edit-pdf/index.html`), not generated by `build-pages.mjs`,
  so it is committed rather than produced — the `.gitignore` rule that hides the generated pages
  re-includes it explicitly.
- **D2 — The edit is the engine's `edit_text`, not a new operation.** The engine already replaces
  one show-text operand by value, as an incremental update that preserves the original bytes. The
  workspace's job is to *target* it (which line the user clicked) and to make the result
  downloadable. A new engine operation would be `SL-5.TEXTEDIT.02` and is not this slice.
- **D3 — Undo is a stack of document states, not a mutation journal.** The journal (`SL-5.EDIT.01`)
  does not exist. Re-deriving a state by replaying a journal is also not possible without one. The
  workspace therefore keeps the document's bytes for each step and restores them verbatim, which is
  exact — at the cost of memory, which is bounded by capping the history depth. This is honest
  undo; it is not the spec's model, and the page says so.
- **D4 — The viewer is not modified.** The viewer's read-only contract is asserted by its own
  harness leg and by the extension's copy. The workspace gets its own page and its own module; the
  two share the engine's wire protocol, not their code.
- **D5 — The render op now reports the transform it used.** The text layer lives in PDF user space
  (points, y-up, origin at the `/MediaBox`'s lower-left) and the canvas lives in device pixels
  (y-down, origin top-left). The mapping between them is not a scale and a flip: a page with
  `/Rotate 90` runs its text *down* the canvas and swaps its axes, and a `/MediaBox` that does not
  start at (0, 0) is translated by that origin. A shell that assumes "scale by the DPI, flip y" —
  which is what the reader does — puts the click target on the wrong pixels of exactly the pages
  where it matters. So `render` now answers with `ctm`, the six matrix elements it used, and the
  workspace maps the text layer through the engine's own arithmetic rather than a second
  implementation of it. This is a **read-only addition** to an existing op: no new operation, no
  new engine capability, and the transform it reports is the transform it used.

## Slice 1 — what ships

- [x] **A1 — The route and its page.** `/edit-pdf/` is a static page under the deployment root, with
      its own script module and stylesheet, and it is precached by the service worker so it opens
      offline.
- [x] **A2 — The document surface.** The workspace renders every page of the open document as a
      canvas with a selectable text layer over it, the way the viewer does, and it re-renders after
      every operation. The text layer is placed through the transform the engine reported, so a
      turned or off-origin page gets its text where the engine drew it.
- [x] **A3 — Click-to-edit.** Clicking a line in edit mode opens an inline editor over it;
      committing it runs the engine's text edit against the open document and re-renders.
- [x] **A4 — Page operations.** Rotate, delete, reorder, duplicate and insert-blank apply to the
      open document and are undoable.
- [x] **A5 — Undo and redo.** A bounded history of document states, restored verbatim.
- [x] **A6 — Download.** The edited document leaves the tab as a Blob URL, on the user's click.
- [x] **A7 — The no-upload guard.** The workspace installs the same recorder the tools page does and
      asserts, after every operation, that no request carried a byte of the document.
- [x] **A8 — Evidence.** Unit tests for the workspace's pure logic (history, the operation
      builders, the search ladder, the page geometry) and a browser leg (`xtask browser-check
      --only editor`) that opens the route, edits a line, undoes it, redoes it, and reads the
      downloaded bytes back.

### How the edit finds the line the user clicked

The engine replaces the **first** show-text operand on the page that carries the search text, and a
line's recovered text is *assembled* from several operands joined by synthesised spaces. So:

1. the whole line is tried first — the user's literal intent, and right whenever the line is one run;
2. then the line's longest words, because a word is usually a whole operand;
3. and after every attempt the workspace **re-reads the line back from the produced document** and
   checks that the line the user clicked is the line that changed.

That last step is what makes the editor honest. A page that repeats the words higher up would have
the engine edit *that* line; the check catches it, the change is discarded, and the next candidate
is tried. Without it the workspace would silently change the wrong line and show a document that
looks edited.

## Out of scope for this slice

- Paragraph re-flow (`SL-5.TEXTEDIT.02`), fonts that lack the needed glyph
  (`SL-5.TEXTEDIT.04`), annotations as first-class objects (`SL-5.ANNOT.*`), image editing
  (`SL-5.TEXTEDIT.05`), vector selection (`SL-5.TEXTEDIT.06`).
- The mutation journal and its undo groups (`SL-5.EDIT.01`, `SL-5.EDIT.02`) — the workspace's
  snapshot history is a stand-in, not the spec's model.
- Form authoring (`SL-5.FORM.06`), signing inside the workspace (the sign card does it today),
  redaction (`SL-5.REDACT.*`).

## Risks

| Risk | Mitigation |
|---|---|
| The workspace grows a second document renderer beside the viewer's | The rendering is the engine's `render` op and the same text-layer protocol the viewer uses; the workspace's renderer is small and its tests cover the geometry, not the pixels. The viewer is not touched, so the two cannot drift in a way that breaks a shipped surface. |
| Byte-snapshot undo is memory-hungry on a large document | The history is capped at a fixed depth and each state is the document's bytes; the cap is a constant in one place. |
| An edit that the engine cannot address is silently dropped | The engine's refusal is surfaced verbatim, the text layer's own marker (`lowConfidence`) is carried through so the page can say when a page's text was not fully recovered, and the line-read-back check catches an edit that landed on the wrong line. |
| The route drifts from the site's design system | The page loads the same `style.css` the viewer is served, so the tokens and the shell are one set; only the workspace's own three-column layout is a separate stylesheet. |
